# Ovian on OpenFantasyMaps: a proposal

Status: **idea, nothing built yet.** This note sketches how an Ovian world could live on a map from [FantasyMaps / OpenFantasyMaps](https://www.fantasymaps.org). FantasyMaps' own stated aim is "a shared, persistent world where what players do leaves traces — a slow-paced MMRPG built on top of the maps", and Ovian is a slow-paced MMO strategy game.

## What OFM already has

| Piece | What it gives us |
|---|---|
| The atlas | Fantasy worlds (Toril, Middle-earth, homebrew) georeferenced in Web Mercator, with vector layers: coasts, rivers, forests, mountains, settlements. |
| [georender](https://github.com/openfantasymap/georender) | Styled slippy-map tiles from a JSON ruleset: `/{map}/{ruleset}/{z}/{x}/{y}.png`, plus TileJSON. Sources can be GeoJSON, PostGIS, MVT or geocontext. |
| [geomqtt](https://github.com/openfantasymap/geomqtt) | Redis GEO sets mirrored to MQTT topics keyed by tile, `geo/<set>/<z>/<x>/<y>`. It sends a snapshot on subscribe, then live `add`/`move`/`remove` events, and object attributes as `obj:<id>` hashes. |
| [ofm-shared-world](https://github.com/openfantasymap/ofm-shared-world) | A FoundryVTT client of geomqtt: tables see each other's actors moving on the same world. |
| OFM MCP server and gazetteer | Lore and wiki links for real (fantasy) places. |

Ovian already speaks MQTT and keeps its rules in data, so the mapping is mostly adapters.

## The mapping

```
OFM world (vector data, gazetteer) ──import──▶ Ovian world grid ──▶ engine (Rust)
                                                     │
Ovian server ──ofm_bridge plugin──RESP──▶ geomqtt ──MQTT geo/ovian-<world>/z/x/y──▶ OFM map, Foundry tables, Unity/Unreal
                                                     ▲
georender tiles (an "ovian" ruleset) ────────────────┴──▶ Ovian map screens (ledger + diorama)
```

1. **World geometry: a `geo` map generator.**
   - A pack names an OFM world and a bounding box. Ovian keeps its integer tile grid, because the rules need it, but each tile becomes a fixed cell of that box: for example 2 km, at a chosen Web Mercator zoom.
   - A Python importer, the customisable side, reads the OFM vector layers for the box and rasterises them into a terrain grid (`water`, `plain`, `forest`, `hill`, `mountain`, `marsh`). It writes the grid as a pack data file.
   - The Rust engine gets a third generator next to `grid` and `islands` that reads that file instead of noise. Settling rules, travel and the WASM client keep working unchanged.

2. **Places.**
   - Gazetteer settlements (Waterdeep, Baldur's Gate, …) become neutral, non-player cities that can be raided or traded with.
   - Regions become starting areas: "found your city in the Sword Coast".
   - Player villages take a real position and can show the OFM lore link of the nearest place.

3. **The map screens** stop drawing coloured squares. They show georender tiles from an `ovian` ruleset (parchment, or 0 A.D.-like terrain for the diorama) in MapLibre, with villages, movements and borders as live overlays.

4. **Shared world: an `ofm_bridge` server plugin.**
   - The plugin writes every village to a geomqtt GEO set (`GEOADD ovian:<world> lng lat village:<id>`) with attributes (`HSET obj:village:<id> owner civ population icon`).
   - Marching armies are moving objects. The plugin knows each movement's start, end and timing, so it interpolates their positions every few seconds and removes them on arrival.
   - The result: a FoundryVTT table with ofm-shared-world, or the OFM map itself, sees Ovian armies crossing the continent in real time, and Ovian clients can show the other tables' parties as ghosts on the world map.
   - The plugin is outbound only at first. Everything goes through the existing hook system (`ovian_modules`, `ovian_battle_resolved`, the movement jobs), so the core does not change.

5. **Travel and scale.** Speeds stay in tiles per hour, and a tile is now a known distance. Reports and the UI can say "3 days' march to Neverwinter".

## Suggested order

1. Importer, `geo` generator and the georender basemap: a playable world on a real fantasy map.
2. Outbound geomqtt bridge: villages and marching armies visible to other OFM tools.
3. Inbound: Foundry parties and other worlds' events as ghosts or quests in Ovian.

## Open questions

- **Which world?** Toril is Wizards of the Coast property, which is fine for a private table but risky for a public game. An original OFM world, or one generated by OFM's continent tools, avoids that.
- **Which endpoints and credentials?** The public geomqtt at `wss://geomqtt.fantasymaps.org/mqtt`, or a self-hosted instance next to Ovian? Is there a tile and vector endpoint (MVT, PostGIS) Ovian may read the world from?
- **How much should a world move?** If the OFM map is edited (a new river), should the Ovian grid be re-imported between seasons only?
